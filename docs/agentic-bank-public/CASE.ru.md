# Halyk AI Challenge

**Постройте AI-агента, который читает «грязные» финансовые документы и точно определяет,
нарушены ли условия (ковенанты) корпоративных кредитов.**

---

## 1. Задача

У каждого заёмщика есть кредитный договор с несколькими финансовыми ковенантами — такими же
условиями, какие банк реально прописывает в кредитном соглашении.

Для **каждого ковенанта каждого заёмщика** агент должен определить:

1. **`status`** — `COMPLIANT` (соблюдён) или `BREACH` (нарушен).
2. **`actual`** — фактическое значение показателя, который ограничивает ковенант.
3. **`evidence_txn_id`** — если нарушение связано с конкретной транзакцией, её ID.

---

## 2. Датасет

Один архив на весь датасет:

| Файл / папка | Что это |
|------|---------|
| `master_ledger_2025.csv` | Полный реестр транзакций по **всем** заёмщикам, одна таблица. Без колонки категории, разные валюты. Расходы записаны отрицательными суммами, поступления — положительными. |
| `documents/` | **Одна папка** со всеми PDF-документами датасета. Имена файлов — **непрозрачные хеши** (например `04eee2e9ba8c.pdf`) и не раскрывают ни заёмщика, ни тип документа. Что это за документ и к какому заёмщику он относится, можно понять только открыв и прочитав его. |
| `submission_template.json` | Точный список сценариев и ковенантов, на которые нужно ответить, с заранее заданными пустыми ячейками. **Заполните и отправьте.** |

---

## 3. Ожидаемый результат

Вы отправляете **один файл JSON**, `submission.json`, точно по образцу
`submission_template.json`: `scenario_id` заёмщика, затем **номер пункта** ковенанта, затем ячейка
ответа.

```json
{
  "team": "your-team-name",
  "contact_email": "you@example.com",
  "model": "claude-sonnet-5",
  "answers": {
    "T1": {
      "6.1": { "status": "COMPLIANT", "actual": 1850000.00, "evidence_txn_id": null },
      "6.2": { "status": "BREACH",    "actual": 5400000.00, "evidence_txn_id": null },
      "6.3": { "status": "BREACH",    "actual": 300000.00,  "evidence_txn_id": "TXN-T1-0020" }
    },
    "T2": {
      "6.1": { "status": "BREACH",    "actual": 450000.00,  "evidence_txn_id": "TXN-T2-0001" },
      "6.2": { "status": "COMPLIANT", "actual": 3.00,       "evidence_txn_id": null },
      "6.3": { "status": "COMPLIANT", "actual": 3500000.00, "evidence_txn_id": null }
    }
  }
}
```

**В шаблоне уже есть все ячейки.** Вы не создаёте ключи — вы заполняете три пустых поля в каждой
готовой ячейке. Единственная ваша задача — понять, к какой ячейке относится прочитанный ковенант.

### Как найти нужную ячейку

**Ковенант** — простая половина: ячейки обозначены номером пункта, под которым ковенант напечатан
в кредитном договоре. Пункт 6.2 договора — это ячейка `"6.2"`.

**Заёмщик** требует одного шага. В документах заёмщик обозначен названием компании и `account_id`,
а в шаблоне — `scenario_id`. Связывает их леджер: **ID каждой транзакции начинается с `scenario_id`
того заёмщика, на счёте которого она находится:**

| Строка леджера | |
|---|---|
| `txn_id` = `TXN-P1-0039` | `scenario_id` — это **`P1`** |
| `account_id` = `ACC-7801` | счёт заёмщика |

Значит, документ, в котором указан `ACC-7801`, относится к заёмщику, чьи ответы идут под ключом
`"P1"`. Каждый `account_id` соответствует ровно одному `scenario_id`.

### Правила ячеек

| Поле | Что указывать |
|---|---|
| `status` | Ровно `"COMPLIANT"` или `"BREACH"`, заглавными. |
| `actual` | **Положительное** число до **2 знаков после запятой**. Суммы — в долларах; коэффициенты — обычным числом. |
| `evidence_txn_id` | Единственная транзакция, определяющая результат, или `null`. Для коэффициентных и агрегатных тестов в ключе стоит `null` и принимается любое значение. |

#### Что такое `actual`

**Фактическое значение показателя, который ограничивает ковенант.** Если пункт ограничивает X
суммой $300,000, то `actual` — это X: ниже лимита при соблюдении ковенанта, выше при его
нарушении. Указывайте его в обоих случаях.

- Всегда **положительное** число, в том числе для расходов. В леджере списания отражены
  отрицательными суммами; `actual` — это модуль. Суммы — в долларах, коэффициенты — обычным
  числом (`1.68`, а не `1.68x`).
- Отдельные ковенанты допускают превышение при выполнении оговорки либо применяются только при
  срабатывании условия. В таких случаях `actual` — по-прежнему фактическое значение показателя:
  оно может быть выше лимита при статусе `COMPLIANT`. Указывайте именно его, а не значение
  условия, и не `null`.

#### Что считается доказательством

`evidence_txn_id` — это **единственная транзакция, определяющая результат**: та, чья
переклассификация, включение, исключение или исправление и приводит к нарушению ковенанта. Уберите
её — и вердикт изменится.

Транзакция, которая лишь вносит вклад в сумму, доказательством **не является**: ни самая крупная
строка в проверяемой категории, ни последняя перед закрытием периода, ни та, что случайно вывела
накопленную сумму за порог.

Там, где результат не определяется одной транзакцией — коэффициентные тесты, агрегатные лимиты, —
в ключе стоит `null`. В таких ячейках указывать нечего, поэтому присланное значение не
учитывается — в том числе `null`. **Эти 0.20 не начисляются автоматически, а зарабатываются:
они убывают вместе с `actual` по той же шкале.** Точное значение сохраняет все 0.20, ошибка в
2.5% — половину, ошибка в 5% (а также отсутствующий или нечисловой `actual`) — ноль. Поэтому
угадывать идентификатор транзакции в таких ячейках не нужно: платит верное число.

Не переименовывайте, не добавляйте и не удаляйте ключи — пропущенная ячейка не засчитывается. Файл
должен быть **корректным JSON с ключами шаблона**; повреждённый JSON или неверные типы значений
делают затронутые ячейки неоцениваемыми, а неоцениваемая ячейка не засчитывается.

Заполните также верхнеуровневые поля `team`, `contact_email` и `model`.

## 4. Оценка

Каждый ковенант — одна **ячейка**. Каждая ячейка получает оценку от 0 до 1, после чего
ячейки **взвешиваются по сложности** при подсчёте итогового результата.

| Компонент | Баллы | За что начисляется |
|---|---|---|
| `status` | **0.50** | Ровно `"COMPLIANT"` или `"BREACH"`, совпадающее с ключом. |
| `actual` | **0.30** | Оценивается по убывающей шкале, а не «верно/неверно» — см. ниже. |
| `evidence_txn_id` | **0.20** | Ровно тот `txn_id`, который указан в ключе. Если в ключе стоит `null`, эти баллы убывают вместе с `actual` по той же шкале — см. ниже. |

**`actual` оценивается по шкале, а не по принципу «всё или ничего».** Точное совпадение
даёт полные 0.30; далее балл убывает линейно с **относительной** погрешностью и обращается
в ноль при 5%:

```
баллы = 0.30 × max(0, 1 − e / 0.05)        e = |ваше значение − ключ| / |ключ|
```

То есть погрешность округления почти ничего не стоит, ошибка в 2.5% даёт половину, а
ошибка в 5% — ноль. Указывайте `actual` с двумя знаками после запятой и не округляйте до
тысяч.

| Ситуация | Результат |
|---|---|
| `status` неверен | **Вся ячейка — 0**, какими бы точными ни были остальные поля. |
| Ячейка пропущена, переименована или добавлена | **0** за эту ячейку. |
| `status` не равен в точности `COMPLIANT` / `BREACH` | **0** за эту ячейку. |
| `actual` отсутствует, не является числом либо отличается на 5% и более | Теряются 0.30, **а также 0.20**, если в ключе для доказательства стоит `null`. |
| `actual` отличается частично | Убывают и 0.30, **и 0.20**, если в ключе для доказательства стоит `null`. |
| Повреждённый JSON | Затронутые ячейки становятся неоцениваемыми, а неоцениваемая ячейка — **0**. |

Пустая и неверная ячейка стоят одинаково, поэтому заполняйте все ячейки.
