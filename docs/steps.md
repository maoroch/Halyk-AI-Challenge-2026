# ТЗ: AI-агент для проверки кредитных ковенантов (Halyk AI Challenge)

> Документ — техническое задание для передачи ИИ-агенту-разработчику (например, Claude Code).
> Составлено на основе официального `CASE.ru.md` и анализа реального загруженного датасета
> (не абстрактных предположений).

---

## 1. Суть задачи

Построить агента, который на входе получает:
- кредитные договоры и сопутствующие документы заёмщиков (PDF, "грязные", вперемешку с нерелевантным шумом),
- реестр всех банковских транзакций за год (CSV),

а на выходе для **каждого ковенанта каждого заёмщика** определяет:

| Поле | Значение |
|---|---|
| `status` | `"COMPLIANT"` или `"BREACH"` — ровно так, заглавными |
| `actual` | фактическое значение показателя, ограничиваемого ковенантом; положительное число, 2 знака после запятой |
| `evidence_txn_id` | ID единственной транзакции, определяющей вердикт, либо `null`, если тест не завязан на одну транзакцию (коэффициентные/агрегатные тесты) |

Результат — **один файл `submission.json`**, заполненный строго по структуре `submission_template.json` (ключи не создаются, не переименовываются, не удаляются — только заполняются 3 пустых поля в каждой готовой ячейке).

## 2. Датасет — что реально в нём есть (проверено, не предположение)

### 2.1 Документы (`documents/`, 96 файлов)
- 95 PDF + 1 decoy CSV (`4a5315740e89.csv` — логи сервера, не имеет отношения к финансам, чистый шум в формате-обманке)
- 1 файл битый / 0 байт (`82954f7cc62a.pdf`) — намеренный edge-case на устойчивость парсера, агент не должен падать на этом файле
- Имена файлов — случайные хеши, **не несут информации** о заёмщике или типе документа
- Типы релевантных документов: кредитные договоры (15–18 стр., статьи 1–25), аудиторские записки/промежуточные ведомости (draft, от разных аудиторских фирм), KYC/AML-досье (проверка контрагентов, политика связанных сторон)
- Типы decoy-документов: HR-политики, бренд-гайды, отчёты об IT-инцидентах, страховые продления, комплаенс-процедуры не по теме кредитов — **это не мусор для игнорирования "на глаз"**, они по формату неотличимы от релевантных без прочтения содержимого
- **Ловушка на entity resolution**: в датасете есть компании с почти идентичными названиями (например `Shymkent Refinery JSC` vs `Shymkent Refinery Services JSC`) — агент обязан различать их по `account_id`, а не по фаззи-совпадению имени

### 2.2 Реестр транзакций (`master_ledger_2025.csv`)
- 1473 строк, 561 уникальных `account_id`
- Из них к реальным сценариям относятся только **12 счетов** (~56 транзакций на каждый, итого ~671 строка релевантны, ~800 строк — чистый шум на посторонних счетах)
- Колонки: `txn_id, date, account_id, counterparty, description, amount, currency`
- Без колонки категории — категория расхода определяется только по `description` + правилам из документов
- Расходы — отрицательные суммы, поступления — положительные; `actual` в ответе всегда положительное (модуль)
- **`txn_id` содержит `scenario_id`**: `TXN-P1-0039` → сценарий `P1`. Связь `account_id ↔ scenario_id` — по факту первой транзакции этого счёта в леджере

### 2.4 `ground_truth.json` — **только для локальной валидации**
В нашем распоряжении оказался файл с эталонными ответами по этим же 12 сценариям.

**Критично:** это не для копирования в финальный `submission.json`. На приватном датасете (реальная оценка, 9 августа) будут **другие** сценарии/документы/леджер — эталона к ним не будет. `ground_truth.json` используется исключительно как **автоматический локальный скорер**: прогнали пайплайн → сравнили с эталоном по формуле из раздела 4 `CASE.ru.md` → увидели реальную точность агента до дедлайна. Любой хардкод ответов из этого файла в логику агента — прямой путь к нулю на приватном датасете и бессмысленная трата времени сейчас.

## 3. Бизнес-логика ковенантов (ключевая сложность)

Ковенанты в договоре (Статья 6, пункты 6.1–6.3) — не голые числа. Формулировка содержит **интерпретационные правила**, физически расположенные в *других* документах того же заёмщика:

- **EBITDA-тесты**: "Скорректированная EBITDA" включает статьи, которые **аудитор** признал подлежащими обратному добавлению — это в аудиторской записке, не в договоре
- **Категорийные лимиты (напр. Capex)**: сумма, которую аудитор классифицировал как относящуюся к категории, засчитывается **независимо от исходного счёта проводки** в леджере
- **Related-party тесты**: принадлежность контрагента к аффилированным лицам определяется по политике связанных сторон из **KYC-досье**, а **не** по назначению платежа в `description`
- Часть ковенантов допускает превышение при выполнении оговорки (carve-out) — `actual` в этом случае всё равно фактическое значение показателя, а не "результат с учётом оговорки"

**Вывод для архитектуры:** правильный ответ по одному ковенанту = договор (порог + тип теста) + аудит/KYC (правило переклассификации) + леджер (сырые цифры), сведённые воедино для конкретного заёмщика. Это не RAG-поиск "похожего текста", а точная сборка фактов из строго определённого набора документов на заёмщика.

### 3.1 Логика `evidence_txn_id` (отдельный нетривиальный алгоритм)

Это **не** "самая крупная транзакция в категории" и не "последняя перед закрытием периода". Это единственная транзакция, чьё удаление меняет вердикт — то есть маргинальная операция, которая переводит накопленную сумму через порог. Нужен алгоритм: отсортировать релевантные транзакции → накопить сумму → найти ту, которая пересекает лимит → проверить, что без неё вердикт действительно меняется на противоположный.

Если тест коэффициентный/агрегатный — в ключе `null`, и это осознанное архитектурное решение, а не "не нашли транзакцию".

## 4. Формула оценки (для локального скорера)

```
за ячейку:
  status  — 0.50, всё или ничего (неверный status = 0 баллов за всю ячейку)
  actual  — 0.30 × max(0, 1 − e/0.05), где e = |ответ − эталон| / |эталон|  (относительная погрешность, 0 при ошибке ≥5%)
  evidence_txn_id — 0.20 при точном совпадении; если в ключе null — эти 0.20 тоже
                    убывают вместе с actual по той же шкале (не начисляются отдельно)

Итог = сумма баллов по ячейкам, взвешенная по сложности ячеек (комплексность на стороне организаторов)
```

Пустая ячейка = невалидный JSON = неверный `status` → **везде 0**. Значит локальный валидатор должен проверять 100% заполненность и валидность типов ДО оценки логики.

## 5. Целевая архитектура

**Модульный монорепо, один процесс** (не микросервисы с HTTP — из-за жёсткого окна в 3 часа на приватном прогоне сетевые вызовы между контейнерами — лишний риск отказа). Модули как Python-пакеты с чёткими границами и Pydantic-контрактами, вызываются как импорты.

```
halyk-ai-agent/
├── services/
│   ├── ingestion/                 # чтение zip/папки, реестр файлов, обработка битых PDF
│   ├── document_classifier/       # тип документа + привязка к account_id/заёмщику
│   ├── covenant_extractor/        # из договора: тип теста, лимит, период, carve-out
│   ├── adjustment_extractor/      # из аудита/KYC: EBITDA add-back, capex reclass, related-party список
│   ├── ledger_service/            # фильтрация по account_id, агрегации, категоризация
│   ├── decision_engine/           # применяет adjustment-правила к транзакциям, считает actual + status
│   ├── evidence_selector/         # алгоритм маргинальной транзакции (раздел 3.1)
│   ├── response_builder/          # сборка submission.json по шаблону
```

## 6. Пайплайн по шагам

1. **Ingestion**: распаковка, реестр файлов, пропуск/логирование битых (0-байтных) файлов без падения процесса
2. **Классификация документов**: для каждого файла — релевантен ли (loan agreement / audit / KYC vs decoy) и к какому `account_id` относится (по содержимому, не по имени файла); проверка на entity resolution ловушки (похожие названия компаний — сверять по `account_id`, не по имени)
3. **Извлечение ковенантов**: по каждому релевантному договору — 3 пункта (6.1–6.3): тип теста, лимит, период, наличие carve-out
4. **Извлечение правил переклассификации**: по аудиторским/KYC документам заёмщика — EBITDA add-back статьи, capex-переклассификация, список related-party контрагентов
5. **Обработка леджера**: фильтрация по `account_id` данного сценария (игнорируя ~550 нерелевантных счетов), применение правил переклассификации из шага 4
6. **Расчёт**: `actual` и `status` по каждому из 3 ковенантов на основе типа теста (сумма / коэффициент / доля)
7. **Подбор evidence**: маргинальный анализ (раздел 3.1) там, где тест завязан на одну транзакцию; `null` — где нет
8. **Сборка `submission.json`**: подстановка в шаблон, ничего лишнего/недостающего
9. **Валидация**: структурная (`validate_submission.py`) → локальный скор (`score_against_ground_truth.py`, только на dev-сценариях) → готово к отправке

## 7. План тестирования

- **Golden-set уже есть**: все 12 сценариев из `ground_truth.json` — можно замерять точность агента локально прямо сейчас, до открытия официального открытого/приватного датасета
- Реализовать `score_against_ground_truth.py` строго по формуле раздела 4 — чтобы локальный скор был сопоставим с тем, что покажет реальная оценка
- Отдельно тестировать устойчивость: битый PDF, decoy-документы (не должны попадать в расчёт), похожие названия компаний (не должны перепутаться)
- Как только выйдет официальный открытый датасет (6–8 августа) — прогнать тот же пайплайн без изменений в логике (только смена входных данных) — это и есть проверка, что решение не переобучено под конкретный сэмпл
